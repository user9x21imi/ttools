# Передача обновлений приложений в ttools

ttools устанавливает и обновляет приложения как проверенный комплект. Агент
приложения готовит исходники и метаданные для PR; GitHub Actions собирает
платформенные ZIP и `suite-update.json` с SHA-256. Лаунчер берёт опубликованный
манифест и архивы из Releases. Нельзя зашивать ключ хранилища в клиент или
загружать релизы напрямую из пользовательской машины.

Сейчас используется GitHub Releases публичного репозитория `user9x21imi/ttools`.
Это отдельное хранилище архивов, но не приватное: анонимный клиент не сможет
скачивать файлы из закрытого хранилища без авторизации. Для настоящего private
storage нужен настроенный сервер или объектное хранилище и безопасная схема
выдачи доступа. Секреты загрузки должны оставаться только в GitHub Actions.

## Общий промпт для агента приложения

```text
Подготовь новую версию [НАЗВАНИЕ ПРИЛОЖЕНИЯ] для включения в комплект ttools.

Репозиторий интеграции: https://github.com/user9x21imi/ttools
Твоя зона: components/[ИДЕНТИФИКАТОР] и связанные с ней исходники/документация.

Сначала прочитай components/[ИДЕНТИФИКАТОР]/HANDOFF.md, app.json,
update.json, текущий код установщика и docs/INSTALL.md. Сохрани терминальный
интерфейс, существующие пользовательские данные и платформенные ограничения.
Не меняй авторизацию, VPN-backend, системные права или формат сессий, если это
не является частью задачи и не описано отдельно.

Обнови исходники приложения, его локальный install/update контракт, версию в
app.json и components/versions.json. Повысь версию комплекта в ttools/__init__.py
и pyproject.toml до следующего preview, чтобы выпуск получил новый уникальный
тег. Обнови SHA-256 инвентарь и проверяемые
зависимости. Если компонент поставляется архивом или wheelhouse, укажи точный
источник, версию, лицензию и SHA-256; не добавляй изменяемую ссылку без проверки.
Для нативного бинарного payload приложи воспроизводимые шаги сборки и тесты
для каждой заявленной платформы. Не клади в PR аккаунты, токены, сессии,
реальные сообщения или другие пользовательские данные.

Повышение версии всего комплекта ttools нужно согласовать с сопровождающим
репозитория. Не создавай GitHub Release и не загружай файлы на внешний сервер
самостоятельно. Передай готовые изменения PR и краткий отчёт: что изменилось,
какие платформы собраны, какие проверки выполнены и что осталось непроверенным.
После принятия PR комплект собирается CI; установщик принимает только HTTPS
архивы, чьи SHA-256 и полный bundle inventory совпали с манифестом.
```

## Особенности компонентов

### tspotify

Меняй исходники и пакет в `components/tspotify`. Сохраняй `install.py`, локальный
runtime protocol и `update.json`. В smoke-режиме используй `--demo --no-splash`;
не выполняй OAuth и не запускай воспроизведение при сборке. Указывай реальные
платформы и версии движка. Пользовательская авторизация и настройки не входят
в пакет.

### ttelegram

Меняй `components/ttelegram`, сохраняя пользовательскую базу авторизации и
миграции. Для Linux обновляй исходники и зафиксированные wheels. Нативный
Windows payload обновляй только вместе с `windows-native-package.json`, SHA-256,
полным inventory и лицензиями; проверяй его офлайн-установку на Windows CI.
Не заявляй поддержку платформы по одной успешной компиляции. Демонстрации
используют вымышленные данные и изолированную сессию.

### TVPN

Меняй исходники в `components/tvpn/source`, версию и платформенные установщики.
Не подключай настоящий VPN в тестах и не выводи приватный IP. Сохраняй явное
согласие пользователя и штатные проверки прав. Любое изменение привилегированного
backend требует отдельного описания миграции, отката и проверки каждой ОС.

### tthings

Меняй исходники в `components/tthings/source`, версию, реестр режимов и inventory.
Сохраняй действующий terminal renderer API, CPU/FPS ограничения, управление
кадрами со стороны клиента и отсутствие лишних процессов. Внешние ссылки на
проекты не добавляй в устанавливаемый каталог и не считай встроенными режимами.

## Как выпускается комплект

CI собирает платформы из зафиксированных файлов репозитория и формирует
`suite-update.json`. В нём перечислены версии, URL ZIP и SHA-256. Лаунчер
проверяет манифест, архив и полный список файлов до установки, оставляя старую
версию доступной для отката. После слияния версии в `main` успешный CI
автоматически создаёт preview Release, если тег этой версии ещё не выпущен.
Поэтому каждый PR с обновлением приложения должен повысить версию комплекта.

Архивы лежат отдельно от исходников и README, но GitHub Releases публичны.
Нельзя одновременно закрыть архив от людей и дать анонимному клиенту скачать
его. Для приватного хранилища нужны credentials объектного хранилища и сервер,
выдающий клиенту авторизованный или короткоживущий URL. Ключ загрузки хранится
только в GitHub Actions и не попадает в ZIP или исходники.
